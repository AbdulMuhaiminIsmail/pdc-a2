\section{Measurement Protocol}
\label{sec:protocol}
%======================================================================

Every number in this report was obtained under the following protocol. It is
automated, one harness per program (\texttt{measure.sh} for Program 1 and
\texttt{measure\_prog2.sh} through \texttt{measure\_prog6.sh} for the
others), so that it is applied identically to every configuration within a
program.

\begin{itemize}
\item All other applications were closed. Measurements were taken from a
      standalone terminal with the browser, editor and background services
      shut down; the load average was verified to be near zero before
      starting.
\item The laptop was connected to mains power throughout.
\item The CPU frequency governor was set to \texttt{performance}
      (\texttt{sudo cpupower frequency-set -g performance}) and verified by
      reading \texttt{scaling\_governor}.
\item \textbf{Each configuration was run five times and the minimum is
      reported.} In Programs 1, 3, 4 and 5 each invocation of the binary
      already takes the best of several internal repetitions --- five in
      Program 1, three in the other three --- so those figures are the minimum
      over 25 and 15 executions respectively.
\item The minimum \emph{and} maximum across the runs were recorded for every
      configuration, so the run-to-run spread is quoted rather than assumed.
      Spread is reported alongside the numbers throughout; it is below 2\% for
      most configurations but reaches 6--9\% in several, and those cases are
      identified where they occur rather than averaged away.
\item \textbf{Two programs deviate, for stated reasons.} Program 2 produces
      exact instruction counts from a simulator rather than timings, so a
      single run is exhaustive (Section~\ref{sec:p2what}). Program 6 takes
      20--50\,s per run, almost all of it inside the timed region, so it uses
      three repetitions rather than five and runs its comparisons as
      interleaved rounds (Section~\ref{sec:p6profile}). No other section
      departs from the five-run rule.
\item Long sweeps were separated so the machine could return to idle
      temperature between them.
\end{itemize}

No performance figure in this document comes from a single run. Two
diagnostic tables are exceptions and are labelled as such: the
involuntary-context-switch counts in Table~\ref{tab:p1cs} and the core-clock
samples in Table~\ref{tab:p1clock}. Neither is a timing claim --- the first
counts scheduler events and the second samples a hardware register --- and
neither is used to support a speedup number. These two are also the only
tables in this report transcribed by hand rather than generated.

Every other table and figure is produced by a script from a committed CSV
(\texttt{plot\_prog1.py} and \texttt{make\_tables.py} for Program 1, and
the corresponding \texttt{plot\_prog\emph{N}.py} for the rest), so no
number below was copied by hand from a terminal. The raw per-execution data
is committed alongside: \texttt{prog1\_raw.csv} holds 160 rows for the
normal-priority sweep, and each later program commits its own equivalent.

\section{Program 1: Parallel Fractal Generation Using Threads}
%======================================================================

\subsection{The two decomposition policies}

Both policies partition the image by rows, assign work statically, and use no
synchronisation of any kind between threads. They differ only in \emph{which}
rows each thread receives.

\textbf{Block (parts 1--3).} Thread $i$ receives one contiguous span of rows.
Because 1200 is not divisible by 3, 5, 7 or 16, the first
$(\text{height} \bmod T)$ threads absorb one extra row each; without this the
image is left with uncomputed rows and \texttt{verifyResult} fails.

\textbf{Row-cyclic (part 4).} Thread $i$ receives rows $i$, $i+T$, $i+2T$,
\dots{} interleaved across the whole image.

Both are compiled into the same binary and selected at run time by the
\texttt{MANDEL\_BLOCK} environment variable, so both can be measured in one
sweep under identical conditions. This is a single decomposition rule per
policy, applied unchanged at every thread count; nothing is specialised to a
particular value of $T$.

Speedup under block decomposition is emphatically \textbf{not} linear. Its
efficiency falls from 0.96 at two threads to below 0.60 everywhere
afterwards, and the curve is not even monotonic.

\paragraph{The three-thread datapoint.} Three threads (1.62$\times$) is
\emph{slower} than two (1.92$\times$). Adding a thread made the program worse.

The explanation is the interaction between the cost distribution and the
partition boundaries. Cost per pixel is proportional to iteration count:
pixels inside the set run the full 256 iterations, pixels far outside escape
in two or three, a spread of roughly $100\times$. The set is symmetric about
the real axis, which for view 1 lies at row 600, and its body occupies a dense
band around it.

\begin{itemize}
\item At \textbf{two} threads the split falls at row 600 --- exactly on the
      axis of symmetry. Each thread receives one half of the body. The
      partition is accidentally almost perfect, which is why two threads
      achieves 0.96 efficiency.
\item At \textbf{three} threads the blocks are rows 0--399, 400--799 and
      800--1199. The middle block contains essentially the entire dense band,
      so thread 1 performs most of the work while threads 0 and 2 finish early
      and idle. Speedup collapses.
\item At \textbf{four} threads the body is split between threads 1 and 2, so
      the result recovers somewhat --- but those two threads still carry far
      more work than threads 0 and 3.
\end{itemize}

The hypothesis is therefore that block decomposition distributes \emph{rows}
evenly but \emph{work} very unevenly, and that whether a given thread count
happens to be good or bad depends on where its boundaries fall relative to the
image's axis of symmetry. View 2 (Table~\ref{tab:p1v2}) supports this: it is a
zoomed view with a different cost distribution, and its three-thread point
(2.12$\times$) does not collapse in the same way, because the dense region is
not concentrated into a single block at that thread count.

The measurements confirm the hypothesis exactly. Under block decomposition at
four threads the outer threads take roughly \ms{48} while the inner two take
roughly \ms{199}, a $4.2\times$ imbalance, and the profile has the symmetric
``tent'' shape the cost distribution predicts. At eight threads the spread
widens to $13.3\times$ (\ms{9.3} to \ms{124.4}).

The decisive detail is the total. At eight threads the program reports
\ms{124.331} for the whole image, and thread 3 --- the slowest --- took
\ms{124.4}. \textbf{The runtime of a parallel region is the time of its
slowest thread, not the average of its threads.} Seven threads finishing early
contributes nothing; they simply wait at the join. This is why block
decomposition stalls at roughly $3.8\times$ once it has one thread per hardware
context, and why the speedup curve tracks the maximum per-thread time rather
than the total work divided by $T$.

Table~\ref{tab:p1v1} shows block reaching $5.85\times$ at sixteen threads,
which is not a counter-example but the same mechanism read backwards. Doubling
the thread count halves the height of every block, so the densest block --- and
with it the slowest thread --- carries a smaller share of the total. Making the
units finer is what improves block decomposition, and it is the same lever
Program~3 pulls deliberately by launching far more tasks than there are
contexts.

\subsection{Part 4: row-cyclic decomposition}

The fix follows directly from the diagnosis. The problem is not the amount of
work but its assignment, so the assignment is what changes.

Cost varies \emph{smoothly} with row index --- rows 500 and 508 cost almost
the same --- so giving thread $i$ the rows $i, i+T, i+2T, \dots$ hands every
thread a near-identical sample of the whole cost distribution. Each thread
receives some rows from the dense band and some from the sparse margins, in
the same proportion. No communication, no synchronisation, no dynamic work
queue, and the same rule at every thread count.

The result is immediate. At four threads the per-thread times become
\ms{124.9}, \ms{125.2}, \ms{126.0} and \ms{129.4} --- a spread of
$1.0\times$ against block's $4.2\times$ (Table~\ref{tab:p1balance},
Figure~\ref{fig:p1bal4}). As everywhere in this section these come from the
repetition that set the reported minimum, which is why they match
Table~\ref{tab:p1balance} rather than any other run. The
three-thread point rises from 1.62$\times$ to 2.85$\times$, a $1.76\times$
improvement obtained by executing exactly the same instructions on exactly the
same hardware, changing only which thread runs which row.

Efficiency now stays between 0.83 and 0.97 across the entire range up to eight
threads, rather than collapsing after two.

\textbf{The reported eight-thread speedup is $6.66\times$ on view 1 and
$6.52\times$ on view 2} (minimum of five runs, \texttt{nice -20}; see
Section~\ref{sec:p1sched} for why priority is part of the measurement).

\subsection{The eight-thread anomaly: when the bottleneck is not your code}
\label{sec:p1sched}

At normal priority the row-cyclic results contain something that should not
happen: \textbf{seven threads (6.05$\times$) outperformed eight
(5.42$\times$)}, and sixteen (6.13$\times$) outperformed both.

The per-thread timings showed six threads at \ms{67.2}--\ms{67.7} --- agreeing
to better than 1\% --- and one or two threads at \ms{88}--\ms{100}. Crucially,
\textbf{the slow thread was a different thread in every repetition}: thread 3,
then threads 3 and 7, then 7 and 0, then 0 and 7, then 3 again. The work
assignment is deterministic and byte-identical across repetitions, so a
deterministic decomposition cannot produce a non-deterministic straggler. The
cause had to lie outside the program.

The hypothesis: with eight compute threads on eight hardware contexts there is
no context left over for the kernel, the shell or the display server. Whichever
compute thread the scheduler evicts to run that work loses roughly \ms{30},
and because runtime is the maximum, one eviction costs the entire image.

Two independent measurements were used to test this.

Table~\ref{tab:p1prio} is the conclusive result. Raising scheduling priority
improves \textbf{only} the eight-thread configuration, by 22.9\%. Every other
configuration becomes 3--4\% \emph{worse}, because the serial baseline also
runs at elevated priority and drops from \ms{468.5} to \ms{448.6}, reducing
the ratio. That uniform 3--4\% degradation is the control: eight threads
overcomes it and still gains 22.9\%, while four, seven and sixteen threads do
not respond at all.

This is exactly what the hypothesis predicted, including the null results. At
seven threads a context remains free, so there is nothing to preempt and
priority is irrelevant. At sixteen threads oversubscription already absorbs
preemption, so priority is again irrelevant. Only at exactly eight --- full
occupancy with no headroom --- does the effect exist, and removing it recovers
the loss.

With preemption eliminated the curve behaves as the hardware predicts: eight
threads becomes the best configuration at $6.66\times$, and the run-to-run
spread at eight threads falls from 6.6\% to 0.5\%.

\subsection{Part 5: sixteen threads}

\textbf{At normal priority, sixteen threads (6.13$\times$) appeared faster than
eight (5.42$\times$). Under controlled conditions the ordering reverses:
sixteen threads (6.33$\times$) is 5\% \emph{slower} than eight
(6.66$\times$).}

Performance is therefore not meaningfully greater at sixteen threads, and the
apparent gain at normal priority was an artefact.

The reason is that the processor provides only eight hardware contexts. Beyond
that, additional threads do not execute concurrently --- they time-share
contexts that are already saturated, adding context-switch overhead and
scheduling jitter while contributing no additional parallelism. The 8.8\%
run-to-run spread at sixteen threads, against 0.5\% at eight, is that jitter
made visible.

The apparent advantage at normal priority was not a benefit of
oversubscription but a \emph{workaround} for the preemption problem of
Section~\ref{sec:p1sched}: with two threads per context each holding half the
work, an eviction costs half as much and the scheduler can interleave around
it. Once the underlying problem was removed, the workaround became pure
overhead. That the sixteen-thread figure at normal priority (6.13$\times$) sits
so close to the seven-thread figure (6.05$\times$) is the same fact from
another angle --- both are ways of leaving the scheduler room, and neither
exceeds what eight unimpeded threads achieve.

The achieved figure is $6.66\times$ at eight threads, against the handout's
stated target of roughly $7$--$8\times$. Three measured effects account for the
difference.

\textbf{Scaling across physical cores is near-ideal.} Four threads reach
$3.61\times$, an efficiency of 0.902. The decomposition is not the limiting
factor; at four threads the per-thread spread is $1.0\times$.

\textbf{Hyper-Threading contributes $1.845\times$ on top of four cores}
($6.66 / 3.61$). This is unusually high --- typical SMT gains are 1.2--1.3$\times$
--- and it is a property of this workload. The inner loop of \texttt{mandel()}
is a serial dependency chain of floating-point multiplies and adds in which
each iteration's \texttt{z\_re} depends on the previous iteration's. It is
latency-bound with low instruction-level parallelism, leaving pipeline slots
empty that a second thread on the same core can fill almost for free.
Mandelbrot is close to a best case for SMT, and Program~5 will show the
opposite extreme.

\textbf{Turbo headroom is lost at full occupancy.} Table~\ref{tab:p1clock}
shows peak clock holding at 3881--3908\,MHz up to four threads and falling to
3704\,MHz at eight, a drop of 4.6\%. The serial baseline is therefore timed at
a clock the eight-thread run cannot sustain, so part of the ``missing''
speedup was never physically available. Normalising for it gives
$6.66 \times (3881/3704) = 6.98\times$, i.e.\ essentially $7\times$ in
clock-equivalent terms.

This is the expected difference between this machine and the \texttt{myth}
reference. The i7-7700K is a 91\,W desktop part whose all-core turbo (4.4\,GHz)
sits within 2\% of its single-core turbo (4.5\,GHz); the i7-7820HQ is a 45\,W
mobile part in a laptop chassis, where sustaining all eight contexts costs
measurable clock. The gap between $6.66\times$ and the quoted target is
accounted for by that, not by the decomposition.

\paragraph{What this program demonstrates.} The runtime of a parallel region is
set by its slowest participant, so load balance --- a question of
\emph{mapping}, not of code optimisation --- dominates. A static interleaving
achieved this with no synchronisation whatsoever, because the cost function
varies smoothly across the domain. And when measurements became
non-deterministic while the program remained deterministic, the cause was
necessarily outside the program: the eight-thread deficit was a scheduling
artefact of running exactly as many compute threads as the machine has
contexts, not a property of the algorithm.

\section{Program 2: Vectorizing Code Using SIMD Intrinsics}
%======================================================================

\subsection{What is being measured}
\label{sec:p2what}

This program uses the CS149 ``fake'' vector intrinsics, which simulate a SIMD
unit rather than compiling to real AVX2 instructions. Consequently
\emph{nothing in this section is a timing}. ``Total Vector Instructions'' and
``Vector Utilization'' are exact counts of simulated operations: they are
bit-for-bit reproducible, independent of machine load, and identical on every
run. The five-run minimum protocol of Section~2 therefore does not apply here,
and a single run per width is exhaustive rather than merely adequate. Following
the handout, one fake vector instruction is treated as costing one cycle, so
instruction count is the performance measure.

Note also that \texttt{printStats()} is invoked before \texttt{arraySumVector()}
is called, so every figure below describes \texttt{clampedExpVector()} alone.

\subsection{Implementation}

The serial function raises \texttt{values[i]} to the power
\texttt{exponents[i]} by repeated multiplication and clamps the result at
$9.999999$. Three aspects required care.

\paragraph{Divergent trip counts.} Each lane needs a different number of
multiplications. A vector unit cannot let one lane exit a loop early, so the
loop runs until the \emph{slowest} lane in the vector is finished, with
completed lanes masked off. The mask \texttt{maskActive} is recomputed from
\texttt{count > 0} after every iteration and the loop continues while
\texttt{\_cs149\_cntbits(maskActive) > 0}.

\paragraph{The \texttt{y == 0} special case needs no branch.} The serial code
treats a zero exponent separately, returning $1.f$. Initialising
\texttt{result} to $1.f$ and multiplying $y$ times produces $x^y$ for $y > 0$
and leaves $1.f$ untouched for $y = 0$, since such a lane is never active. This
removes a branch that would otherwise have cost an extra mask and a masked
store. The subsequent clamp is likewise applied unconditionally to all active
lanes: a $y = 0$ lane holds $1.f$, which is below the ceiling, so the result is
unaffected.

\paragraph{Partial final vector.} When \texttt{VECTOR\_WIDTH} does not divide
$N$, the last iteration covers fewer than \texttt{VECTOR\_WIDTH} elements.
Enabling only the valid lanes, by passing
$\min(\texttt{VECTOR\_WIDTH},\, N-i)$ to \texttt{\_cs149\_init\_ones}, keeps
the store from writing past $N$ --- \texttt{main.cpp} checks for exactly this and reports
\emph{``You have written to out of bound value''} --- and keeps the dead lanes
out of the utilization statistics.

This is the flaw in the supplied \texttt{absVector()} example, which the
handout invites the reader to find: its loop advances by
\texttt{VECTOR\_WIDTH} under an unconditional all-ones mask, so for
$N \bmod \texttt{VECTOR\_WIDTH} \neq 0$ it reads and writes past the end of the
arrays.

One further initialisation detail matters. \texttt{\_cs149\_vgt\_int} leaves
masked-off lanes at their previous value, so \texttt{maskActive} is explicitly
cleared with \texttt{\_cs149\_init\_ones(0)} before first use. Without this,
lanes beyond the array end would inherit stale values and could appear active.

The implementation was verified across 32 configurations --- widths
$\{2,4,8,16\}$ against $N \in \{1,2,3,5,7,15,17,100\}$ --- all of which produce

\subsection{Why utilization falls}

The cause is \emph{divergence}. The exponents are drawn uniformly from
$[0, 9]$, so lanes within a vector need different numbers of multiplications,
and the vector must keep iterating until its slowest lane finishes. Every
iteration a lane spends already finished is an enabled slot doing no useful
work.

The wider the vector, the more lanes must agree for the loop to stop early ---
and the more likely it becomes that at least one lane drew a large exponent.
With two lanes the expected maximum exponent is well below $9$; with sixteen it
is close to $9$ almost every time, so nearly every vector runs the full nine
iterations regardless of what the other fifteen lanes needed.

To measure this rather than assert it, \texttt{analyze\_divergence.cpp}
reproduces the exact exponent array \texttt{main.cpp} generates (same
\texttt{rand()} sequence, same \texttt{EXP\_MAX}) and counts how much of the
inner loop's lane capacity is useful.

capacity spent on it rises from 61\,256 at width 2 to 87\,856 at width 16.
Inner-loop utilization accordingly falls from 73.2\% to 51.0\%: \textbf{at
width 16 roughly half of all enabled lane-slots in the loop are doing nothing}.

The measured whole-kernel figure (78.8\% at width 16) is higher than the
loop-only figure (51.0\%) because the surrounding instructions --- the two
loads, the store, the initial \texttt{vset}, \texttt{vmove}, and the clamp ---
run with every lane enabled and never diverge. They dilute the divergence
penalty, which is why the measured curve declines more gently than the
underlying mechanism does.

\subsection{Cost, and why wider still wins}

Falling utilization does not mean wider vectors are worse. Total instruction
count drops from 167\,515 to 27\,592, a $6.07\times$ reduction for an
$8\times$ increase in width. Utilization measures \emph{efficiency}; instruction
count measures \emph{cost}. Efficiency falls while cost falls faster.

The marginal returns are the interesting part. Successive doublings of width
reduce instruction count by $1.73\times$, $1.84\times$ and $1.92\times$ --- the
benefit \emph{improves} as vectors widen, approaching the ideal $2\times$.

Two opposing effects explain this. Per-vector fixed overhead (loads, store,
masks, clamp --- roughly a dozen instructions independent of exponent values)
is amortised over twice as many elements at each doubling, which always helps.
Against that, divergence costs more as width grows --- but only up to a point,
because the exponent range is bounded at $9$. Once vectors are wide enough that
almost every one contains a near-maximal exponent, widening further adds
essentially no extra iterations while still halving the number of vectors. The
divergence penalty saturates; the amortisation does not. The loop-iteration
counts show the same saturation directly: $30\,628 \to 18\,642 \to 10\,406 \to
5\,491$, ratios of $1.64$, $1.79$, $1.90$, converging on $2$.

\subsection{Extra credit: vectorized array sum}

\texttt{arraySumVector()} replaces $N$ scalar additions with two phases.

\textbf{Phase 1} folds the array into a single register with $N/W$ vector
additions, leaving $W$ partial sums, one per lane. \textbf{Phase 2} reduces
those $W$ lanes to one value in $\log_2 W$ rounds of
\texttt{hadd} followed by \texttt{interleave}. \texttt{hadd} sums adjacent
pairs and duplicates each result across the pair; \texttt{interleave} then
moves even-indexed lanes into the front half, packing the distinct partial sums
adjacent to one another so the next \texttt{hadd} pairs them. After $\log_2 W$
rounds every lane holds the total.

For $W = 4$ and lanes $[a\;b\;c\;d]$:
\[
[a\;b\;c\;d]
\xrightarrow{\text{hadd}} [a{+}b\;\;a{+}b\;\;c{+}d\;\;c{+}d]
\xrightarrow{\text{interleave}} [a{+}b\;\;c{+}d\;\;a{+}b\;\;c{+}d]
\xrightarrow{\text{hadd}} [T\;T\;T\;T]
\]
where $T = a+b+c+d$. Total cost is $N/W + 2\log_2 W$ vector operations against
$N$ scalar additions, meeting the $O(N/W + \log_2 W)$ target. The
implementation passes for every width tested.

the width, which is why the marginal return to widening improves rather than
degrades once the spread is saturated.

\section{Program 3: Parallel Fractal Generation Using ISPC}
%======================================================================

The image here is $1200 \times 800$ at 256 iterations, smaller than Program~1's
$1600 \times 1200$, so the serial baselines are not comparable between the two
programs. All figures below follow the Section~2 protocol: five runs per
configuration, minimum reported, spread recorded. The sweep was taken at
elevated priority for the reason established in
Section~\ref{sec:p1sched}; run-to-run spread fell to 1--5\%.

\subsection{Part 1: SIMD width alone}

\paragraph{What speedup should be expected?} The ISPC compiler is targeting
\texttt{avx2-i32x8}, so a gang is eight program instances wide and executes on
one core's 256-bit vector unit. Eight single-precision lanes operating in
lockstep gives a ceiling of $W = 8$. No multi-core parallelism is involved at
this stage.

The measured $\progThreeSimdViewOne\times$ is
\textbf{\progThreeSimdViewOnePct\% of the ideal $8\times$}.

Every invocation of the sweep re-measures the serial and the

\paragraph{Why less than $8\times$?} The same mechanism as Program~2:
\emph{divergence}. A gang covers eight horizontally adjacent pixels, and
\texttt{mandel()} contains a data-dependent \texttt{break}. A lane whose pixel
escapes after three iterations cannot leave the loop while its seven
neighbours are still iterating --- it is masked off and the gang continues.
Since pixels inside the set never escape and run the full 256 iterations, any
gang straddling the set's boundary costs as much as its most expensive pixel.
Only gangs entirely inside or entirely outside the set are efficient.

\paragraph{The view comparison confirms it.} The handout suggests comparing
views to test this hypothesis, and the comparison is decisive. View~2 achieves
$\progThreeSimdViewTwo\times$ against view~1's
$\progThreeSimdViewOne\times$ --- \textbf{\progThreeViewGap\% worse}. View~2 is a
deep zoom into the set's boundary, where the structure is finely filamentary
and neighbouring pixels frequently disagree about iteration count. View~1
contains large uniform regions --- the black interior and the empty margins ---
where all eight lanes of a gang agree and no work is wasted. More boundary per
pixel means more divergence means lower speedup, exactly as predicted.

This is the same result as Program~2 reached by a different route: SIMD
efficiency is governed by agreement between lanes, not by the amount of work.

single-core ISPC version. The reason is plain: two tasks can occupy at most two
of this machine's eight hardware contexts, leaving six idle.

\paragraph{How the task count was chosen.} By sweeping it: 2, 8, 16, 32, 64,

\paragraph{Why more tasks than cores wins --- two separate effects.} It is
tempting to say ``more tasks fill more cores'', but the data shows that is only
half the story, and not the larger half.

\emph{Occupancy} explains the climb from 2 to 8 tasks ($9.54\times \to
17.46\times$). With fewer tasks than contexts, contexts sit idle.

\emph{Load balance} explains everything after that. Going from 8 tasks to 16
gains a further 63\% ($17.46\times \to 28.43\times$) --- and that cannot be
occupancy, because at 8 tasks all eight contexts were already busy. It is the
same imbalance Program~1 diagnosed: with exactly one task per context, each
context is stuck with whatever work its task happens to contain, and rows
through the set's body cost far more than rows through the margins. Runtime
becomes the slowest task. Launching more tasks than contexts lets the ISPC
runtime's work queue hand the next task to whichever context finishes first,
which is dynamic load balancing rather than the static interleaving Program~1
had to construct by hand.

Program~1 solved this by choosing the mapping carefully. ISPC solves it by
making the units small enough that the mapping stops mattering.

\subsection{Achieved speedup against the $C \times W$ ceiling}

The theoretical ceiling for this machine is $C \times W = 4 \times 8 = 32$.

\[
\textbf{Achieved: } 29.93\times \;=\; \textbf{93.5\% of } C \times W
\]

The result factors cleanly into its two sources:
\[
\underbrace{5.12\times}_{\text{SIMD, vs } W=8}
\;\times\;
\underbrace{5.84\times}_{\text{multi-core, vs } C=4}
\;=\; 29.93\times
\]
where the multi-core factor is the single-core ISPC time divided by the task
time, $44.262/7.575$.

This decomposition is the whole account of the shortfall, and it is not what a
naive reading of $C \times W$ would suggest.

\begin{itemize}
\item \textbf{The SIMD factor underperforms badly}: $5.12$ against a ceiling of
      $8$, or 64\%. Divergence costs roughly a third of the vector unit.
\item \textbf{The multi-core factor overperforms}: $5.84$ against $C = 4$, or
      146\%. Hyper-Threading is contributing, exactly as in Program~1 where
      eight threads on four cores reached $6.66\times$. The tasks are latency-bound
      scalar-dependency work, which is the case SMT handles well.
\item The two nearly cancel. The product lands at 93.5\% of a ceiling that
      assumed perfect SIMD and no SMT --- \emph{both} of those assumptions are
      wrong, in opposite directions.
\end{itemize}

Correcting for the 4.6\% all-core turbo drop measured in
Table~\ref{tab:p1clock} gives $29.93 \times (3881/3704) = 31.36\times$ in
clock-equivalent terms.

\paragraph{The handout's target was not met.} The assignment states one should
exceed $32\times$. This machine reaches $29.93\times$, or $31.36\times$
normalised for clock. The gap is the same one Program~1 identified: a 45\,W
mobile part sustaining all eight contexts runs below the clock at which its own
serial baseline was timed, and the reference \texttt{myth} machine, a 91\,W
desktop i7-7700K at 4.2--4.5\,GHz, does not pay that penalty. Raising priority
did not close the gap --- it improved precision (spread fell from 8--40\% to
1--5\%) but not the ratio, because the serial baseline sped up by the same
proportion. No configuration of task count reaches $32\times$ on this hardware.

\subsection{Extra credit: threads versus ISPC tasks}

The mechanisms look similar --- \texttt{launch}/\texttt{sync} against
\texttt{create}/\texttt{join} --- but they differ in what they commit the
runtime to.

\paragraph{A task is a queue entry; a thread is a scheduling entity.} Reading
\texttt{common/tasksys.cpp}, the Linux build uses the pthreads backend, which
sizes its pool once:

\begin{quote}\small
\texttt{// We launch one fewer thread than there are cores, since the main
thread here will also grab jobs from the task queue itself.} \\
\texttt{nThreads = sysconf(\_SC\_NPROCESSORS\_ONLN) - 1;}
\end{quote}

On this machine that is $8 - 1 = 7$ workers plus the calling thread. Inspecting
\texttt{/proc/<pid>/task} during a run confirms \textbf{exactly 8 OS threads},
whether 2 tasks or 800 are launched. The task count never changes the thread
count; it only changes how finely the work is divided among a fixed pool. The
queue is bounded at $128 \times 2^{14} = 2\,097\,152$ tasks.

\paragraph{What happens at 10\,000 of each.} Both were measured.

The comparison is stark. Creating 10\,000 threads takes 348\,ms; computing the
entire Mandelbrot image with 200 tasks takes 7.575\,ms. Thread creation alone
would cost forty-six times the work it was meant to parallelise. Threads had to
be created in batches of 500 because 10\,000 simultaneously live threads
approaches the per-user limit (\texttt{ulimit -u} is 55\,995 here, but each
thread reserves an 8\,MB stack).

\paragraph{The deeper difference.} \texttt{create}/\texttt{join} is a statement
about \emph{concurrency}: each thread is an independent entity that the kernel
must schedule, can block, can synchronise with others, and can make progress
independently. \texttt{launch}/\texttt{sync} is a statement about
\emph{available parallelism}: it declares work that \emph{may} run in parallel
and leaves placement to the runtime.

The consequence is that tasks decouple decomposition granularity from hardware
parallelism, and threads bind them together. This is precisely why Part~2 could
be tuned at all: 200 tasks were chosen for \emph{load-balancing} reasons, with
no obligation to own 200 execution contexts. Program~1 had no such freedom ---
every extra thread there was a real OS thread, which is why 16 threads was
measurably worse than 8.

The price of that freedom is expressiveness. Tasks within a launch group have
no ordering guarantees and cannot wait on one another; a task that blocked
waiting for a sibling could deadlock, since the sibling may be queued behind it
on the same finite pool. Threads can block on each other freely. Tasks trade
the ability to synchronise for the ability to be cheap and numerous --- which is
the right trade for data-parallel work, and the wrong one for a pipeline of
communicating stages.

\section{Program 4: Iterative \texttt{sqrt}}
%======================================================================

This program applies Newton's method to $N = 20{,}000{,}000$ values, starting
from a guess of $1.0$. Convergence is fastest for inputs near $1.0$ --- an input
of exactly $1.0$ converges before the loop body executes once --- and slowest
near the ends of the supported $(0,3)$ range. The number of iterations is
therefore a property of the data, which is what makes the input constructions
in Parts 2 and 3 possible.

\subsection{Predicting speedup before measuring it}

A gang is eight lanes wide and runs until its \emph{slowest} lane converges.
So for each group of eight consecutive elements the vector unit issues
$\max(\text{iterations})$ while the serial code issues their sum. That ratio is
the best SIMD speedup an input permits, and it can be computed from the input
array alone, with no timing involved.

\texttt{main.cpp} does exactly this: \texttt{reportInputProfile()} replicates
\texttt{sqrtSerial}'s loop to count iterations per element, then reports the
serial total, the gang-issued total, and their ratio. Every prediction below
comes from that function; every measurement comes from
\texttt{measure\_prog4.sh} under the Section~2 protocol. They were produced
independently.

\paragraph{Part 1 --- as shipped.} With uniformly random values the ISPC
implementation achieves $4.42\times$ from SIMD alone and $27.66\times$ with

$8$), and multi-core contributes a further $6.26\times$ on top of it
($178.261/28.472$). The multi-core factor exceeds $C = 4$ for the same reason
as in Programs 1 and 3 --- Hyper-Threading on latency-bound code.

\paragraph{Part 2 --- maximising speedup.} The constructed best case sets
\emph{every} element to $2.999$.

Two distinct properties matter, and conflating them is easy. First,
\textbf{uniformity} eliminates divergence: every lane in every gang needs
exactly 22 iterations, so no lane ever idles waiting for a neighbour, and the
divergence ceiling rises to the full $8.00\times$. Second, choosing the
\emph{slowest-converging} legal value \textbf{maximises arithmetic per
element}, so the loop body dominates the single load and single store that
bracket it. A uniform array of $1.0$ would be equally divergence-free but would
perform no arithmetic at all, leaving only memory traffic to parallelise.

Result: SIMD speedup rises from $4.42\times$ to $\mathbf{6.50\times}$, and
total speedup from $27.66\times$ to $\mathbf{38.66\times}$.

\textbf{Does it improve SIMD speedup?} Yes, substantially --- a 47\% increase.

\textbf{Does it improve multi-core speedup?} \textbf{No.} The multi-core gain
moves from $6.26\times$ to $5.94\times$ --- if anything slightly \emph{worse}.
This is the more interesting half of the answer. Divergence is a property of
lanes \emph{within} a gang; tasks distribute whole gangs \emph{across} cores.
The two mechanisms are orthogonal. Making lanes agree with each other does
nothing to help cores share work, because the cores were never waiting on lane
disagreement --- they were each running their own gangs. The total speedup
improved only because it is the product of the two factors and one of them
improved.

\paragraph{Part 3 --- minimising speedup.} The constructed worst case sets one
element in every eight to $2.999$ and the rest to $1.0$:
\[
\texttt{values[i]} = \begin{cases}
2.999 & i \bmod 8 = 0 \\
1.0   & \text{otherwise}
\end{cases}
\]

The reasoning is a direct inversion of Part 2. Every gang now contains exactly
one lane needing 22 iterations and seven needing none. The gang runs the full
22 iterations regardless, so the vector unit issues \emph{the same number of
iterations as the serial code does} --- 55{,}000{,}000 in both --- while seven
eighths of its lanes sit masked off. The divergence ceiling collapses to
$1.00\times$.

The period and the alignment both matter. The pattern must repeat every eight
elements, matching \texttt{--target=avx2-i32x8}, and must be phase-aligned to
gang boundaries. Any other period would spread the slow elements across gangs
and some gangs would end up cheap.

Result: $\mathbf{0.89\times}$ --- \textbf{the ISPC version is slower than the
sequential code.} Vectorising this input actively loses.

\subsection{A complete quantitative account}

Speedup factors exactly into two independent terms: how much divergence wastes,
and how a vector iteration compares in cost to a scalar one.
\[
\text{speedup} \;=\;
\underbrace{\frac{\text{serial iterations}}{\text{gang-issued iterations}}}_{\text{divergence ratio}}
\;\times\;
\underbrace{\frac{\text{cost of a scalar iteration}}{\text{cost of a gang iteration}}}_{\text{cost ratio}}
\]

\begin{table}[H]
\centering
\small
\progFourModel
\caption{The divergence ratio is computed from the input data alone; the cost
         ratio is derived by dividing measured time by iteration count. Their
         product is therefore an identity that returns the measured speedup;
         the divergence ratio alone is the part known in advance.}
\label{tab:p4model}
\end{table}

One thing must be said plainly about this decomposition: the right-hand
product is an algebraic identity, not a prediction that could have failed. The
cost ratio is obtained by dividing measured time by iteration count, so
multiplying it back by the divergence ratio necessarily returns the measured
speedup. That the final two columns of Table~\ref{tab:p4model} agree is
arithmetic, not evidence.

What \emph{is} evidence is the divergence ratio itself. It is computed from
the input array alone, before any timing, and it is what the speedup would be
if a gang iteration cost exactly what a scalar iteration costs. Comparing it
against the measurement is therefore a real test, and the residual --- the cost
ratio --- is the quantity worth reading: $0.967$, $0.813$ and $0.887$ across
the three inputs. Those numbers are not free parameters fitted per input; they
are close to one another because they measure the same hardware property, and
their spread is what tells us the per-iteration cost is not quite identical
between the scalar and vector loops.

The cost ratio also explains why the best case reaches $6.50\times$
rather than the full $8.00\times$: an ISPC gang iteration takes $5.61$\,ns
against a scalar iteration's $4.56$\,ns, so eight lanes are processed in the
time of $1.23$ scalar iterations rather than one, and
$8.00 \times (1/1.23) = 6.50$. The extra cost is the mask evaluation and blend
that the scalar loop does not perform.

in Table~\ref{tab:p4results}, which differ by a factor of eight in useful work:

The hand-written version is faster than ISPC on all three inputs, comfortably
meeting the ``nearly as fast or faster'' bar. Per gang iteration it costs
$4.14$\,ns against ISPC's $5.61$\,ns.

\paragraph{Why the best case exceeds $8\times$.} $8.82\times$ is above the
nominal $W = 8$ ceiling, which deserves scrutiny rather than celebration. The
ceiling counts \emph{lanes} and tacitly assumes a vector iteration costs what a
scalar iteration costs. Measured, the AVX2 gang iteration costs $0.91$ of a
scalar iteration, so $8.00 \times (1/0.91) = 8.82$. The compiler generated a
shorter dependency chain for the vector loop than for the scalar one; since
this kernel is latency-bound rather than throughput-bound, that shortening
shows up directly in the time.

Two checks confirm the comparison is fair rather than an artefact. The Makefile
builds everything with \texttt{-march=native}, so the \emph{scalar} baseline
also gets FMA --- disassembling \texttt{sqrtSerial.o} shows FMA instructions but
no 256-bit \texttt{ymm} registers, so it is scalar-with-FMA, not secretly
vectorised (the data-dependent \texttt{while} loop blocks auto-vectorisation).
And rebuilding the intrinsics with \texttt{-ffp-contract=off}, which removes
its FMA entirely, still beats ISPC: $291.5$\,ms against $310.3$\,ms on the best
case. The advantage is code quality, not floating-point contraction.

\paragraph{What this program demonstrates.} SIMD speedup is a property of the
\emph{data}, not only of the code --- the same binary on the same machine ranged
from $0.89\times$ to $6.50\times$ purely on what was in the input array. It is
predictable in advance: counting iterations per element gave the ceiling before
anything was timed, and multiplying by a measured cost ratio reproduced every
result exactly. Vectorisation can be a net loss, and the worst case here is not
contrived so much as adversarial --- a real workload with one expensive element
per eight would behave the same way. Finally, the two levers are independent:
fixing divergence did nothing for multi-core scaling, and no amount of
multi-core scaling would have fixed divergence.

\section{Program 5: BLAS \texttt{saxpy}}
\label{sec:prog5}
%======================================================================

\texttt{saxpy} computes $\text{result} = \alpha X + Y$ over $N = 20$ million
single-precision elements. It is the simplest possible parallel workload:
every element is independent, the access pattern is a pure unit-stride stream,
and the cost per element is identical, so none of the effects that limited
Programs 1--4 --- load imbalance, divergence, scheduling --- can arise here.
The handout asks what speedup ISPC tasks deliver and whether the program can be
substantially improved. It is the one program in the assignment where the
answer has nothing to do with how the work is divided.

\subsection{Part 1: the speedup from tasks}

The shipped program was run five times under the protocol of
Section~\ref{sec:protocol}; Table~\ref{tab:prog5-shipped} gives the result.

\prognFiveTableShipped

\begin{quote}
\textbf{The speedup from using tasks is $\mathbf{\prognFiveTaskSpeedup\times}$
--- distributing the work across all eight hardware threads makes the program
\emph{slower} than running it on one.}
\end{quote}

This is not measurement noise. The single-core ISPC time was
\ms{\prognFiveShippedIspcMs} at its minimum and the 64-task time was
\ms{\prognFiveShippedTaskMs}; the task version was slower in four of the five
paired runs. It is also not a small effect hiding inside a large spread: the
run-to-run spreads were \prognFiveIspcSpread\% and \prognFiveTaskSpread\%, and
the gap between the two minima is larger than either. Programs~1, 3 and~4 each gained between
$5.8\times$ and $6.7\times$ from the same eight hardware contexts. Here they
buy nothing. (Program~6 gains less, $\prognSixSThread\times$, but for an
unrelated reason: it is bounded by a serial fraction, not by memory.)

\subsection{Why: the ratio of arithmetic to memory traffic}

The reason is visible from the source without running anything. Per element,
\texttt{saxpy} performs two floating-point operations --- one multiply, one add
--- and touches three floats. The \emph{arithmetic intensity} is therefore

\[
I = \frac{2 \text{ flops}}{16 \text{ bytes}} = \prognFiveIntensity \text{ flop/byte},
\]

using the 16 bytes per element that Section~\ref{sec:prog5ec1} shows are
actually moved. Compare that with what the machine is built to do. Four
Kaby Lake cores, each with two FMA units of eight single-precision lanes, at
the $\prognFiveAllcoreGHz$\,GHz all-core turbo measured in Table~\ref{tab:p1clock}:

\[
4 \times 8 \times 2 \times 2 \times \prognFiveAllcoreGHz\,\text{GHz}
= \prognFivePeakGflops\,\text{GFLOPS}.
\]

Against a peak memory bandwidth of \prognFivePeakGBs\,GB/s, the machine's
\emph{ridge point} --- the intensity at which the two limits balance --- sits at
$\prognFivePeakGflops / \prognFivePeakGBs = \prognFiveRidge$\,flop/byte. \texttt{saxpy} operates at
$\prognFiveIntensity$\,flop/byte, a factor of $\prognFiveRidgeRatio$ below it. The program achieved
$\prognFiveGflops$\,GFLOPS, which is $\prognFiveGflopsFrac\%$ of the floating-point peak: the arithmetic
units are idle better than $99.5\%$ of the time, waiting on memory. Adding
cores adds more units to keep idle.

\subsection{Achieved bandwidth against the DIMM's theoretical peak}

The machine has one 16\,GB DDR4-2667 module in Channel~A and an empty
Channel~B, so its theoretical peak memory bandwidth is
$2667\,\text{MT/s} \times 8\,\text{bytes} = \prognFivePeakGBs$\,GB/s.

One unit conversion has to be done before that number can be compared with the
program's output. \texttt{main.cpp}'s \texttt{toBW} divides by $1024^3$, so the
figure it prints and labels \texttt{GB/s} is in fact GiB/s. DDR4 transfer rates
are quoted in decimal units. The two forms of the same ceiling are

\[
\prognFivePeakGBs\,\text{GB/s (decimal)}
\;=\;
\prognFivePeakGiBs\,\text{GiB/s (binary)} .
\]

Table~\ref{tab:prog5-all} reports both columns for every implementation, so no
comparison in this section mixes the units.

\prognFiveTableAll

\begin{quote}
\textbf{Both numbers, as required.} Theoretical peak of the installed memory:
$\mathbf{\prognFivePeakGBs}$\,\textbf{GB/s}. Best bandwidth achieved by the
program: $\mathbf{\prognFiveBestDram}$\,\textbf{GB/s}, which is
$\mathbf{\prognFiveBestFrac\%}$ \textbf{of theoretical peak}, reached by
single-core ISPC.
\end{quote}

$\prognFiveBestFrac\%$ of theoretical peak is close to the practical maximum for any real
kernel --- DRAM refresh, row activation and turnaround overheads account for
most of the remaining $15\%$. The program is not leaving performance on the
table. It is already running the memory system nearly flat out, which is
exactly why nothing that adds compute capacity changes the answer.

The right-hand panel of Figure~\ref{fig:prog5scaling} makes the point directly:
every configuration measured, at every thread count, with either store
strategy, lands in a narrow band just below the DIMM's ceiling.

\subsection{Ruling out the alternative explanations}

Two things other than bandwidth could produce a $\prognFiveTaskSpeedup\times$
result, and both were tested rather than assumed.

\paragraph{Task granularity.} The shipped code launches exactly 64 tasks. If
that were too coarse or too fine, the measurement would say more about ISPC's
scheduler than about the machine. The task count was made a compile-time
parameter and swept over the range 1--256
(Table~\ref{tab:prog5-tasks}, Figure~\ref{fig:prog5tasks}).

\prognFiveTableTasks
 The best count was
\prognFiveTaskBestN{} at \ms{\prognFiveTaskBestMs} and the worst was
\ms{\prognFiveTaskWorstMs}, a total range of \prognFiveTaskRange\%.

The shape is not a smooth decline and should not be described as one. Time
rises steadily from one task to eight --- that is, performance gets worse as
the work is spread across more contexts --- and from eight tasks to 256 it is
flat to within 3.5\%, wandering without trend. The two facts together are the
point: the damage is done by the time every context is busy, and subdividing
further neither helps nor hurts. There is no granularity at which tasks win.
This also rules out load imbalance as a contributor, which was the dominant
effect in Program~3: if imbalance mattered, more tasks would help, and past
eight they do nothing at all.

\paragraph{ISPC's task system specifically.} The sweep above still runs
entirely inside ISPC, so it cannot distinguish "bandwidth-bound" from
"something is wrong with \texttt{tasksys}". A separate hand-written AVX2 kernel
was therefore parallelised with plain \texttt{std::thread} and swept over

The small \emph{negative} slope is itself explainable: with the bus already
saturated, extra threads contribute nothing but interleaved access streams,
which reduce DRAM row-buffer locality, plus thread creation and join costs that
the single-threaded version does not pay.

\subsection{Can it be substantially improved? Could it scale linearly?}

\begin{quote}
\textbf{Near-linear speedup: no.} Not by any rewrite. A kernel's execution time
cannot fall below $(\text{bytes moved}) / (\text{achievable bandwidth})$, and
neither term depends on how many cores run it. The bytes are fixed by the
problem statement --- $2N$ elements must be read and $N$ written --- and the
bandwidth is a property of one DDR4-2667 channel. Linear speedup in $T$ would
require bandwidth to grow with $T$, and on this machine it does not grow at
all: a single core already draws \prognFiveBestFrac\% of what the module can supply, so there
is no headroom for a second core to exploit, let alone an eighth.
\end{quote}

\begin{quote}
\textbf{Substantially improved: yes, but only by moving fewer bytes} --- and by
a bounded factor. Section~\ref{sec:prog5ec2} achieves
$\prognFiveNtGain\times$, which is essentially all of the
$\prognFiveNtPredicted\times$ that is theoretically available.
\end{quote}

The distinction matters. "Make it parallel" is the wrong question for this
program; "make it move less data" is the right one. That is the general lesson
of the roofline model, and it is the reason the same eight hardware threads
that were worth $6.3\times$ in Program~3 are worth $0.92\times$ here.

It is worth stating what would actually fix this machine, since it is a
configuration problem rather than a code problem: populating Channel~B would
double the theoretical peak to $42.7$\,GB/s. On a bandwidth-bound kernel
running at \prognFiveBestFrac\% of a single channel, that second module is worth far more
than any amount of rewriting --- and, unlike the rewriting, it would also let
the task version finally do something useful, since one core cannot saturate
two channels.

\subsection{Extra credit: why the multiplier is four, not three}
\label{sec:prog5ec1}

\texttt{main.cpp} computes \texttt{TOTAL\_BYTES = 4 * N * sizeof(float)} even
though the kernel reads two floats and writes one. The missing fourth access is
a read that the program never asked for.

Stores go through the cache. When \texttt{result[i]} is written, the hardware
must first bring the containing 64-byte line into cache so that the parts of
the line not being written are preserved, and so that the cache has a coherent
copy to own. This is a \emph{read-for-ownership}. Because \texttt{result} is
80\,MB and the L3 is 8\,MiB, every line misses, so every line is fetched from
DRAM --- and then immediately overwritten in full and later written back. The
traffic per element is therefore one read of $X$, one read of $Y$, one
read-for-ownership of \texttt{result}, and one writeback of \texttt{result}:
four floats, of which the third is pure waste.

This explanation is testable, and three independent tests confirm it: one
from timing, one from a number the model renders impossible, and one that
reads the traffic off the memory controller.

\paragraph{Test 1: remove the read-for-ownership and see if the time drops by
the predicted amount.} \texttt{\_mm256\_stream\_ps} issues a non-temporal
store, which writes a full line straight to memory without fetching it first.
If the account above is right, traffic falls from $4N$ to $3N$ and the kernel
should speed up by $4/3 = \prognFiveNtPredicted\times$. Measured:
\ms{\prognFiveStoreMs} $\rightarrow$ \ms{\prognFiveNtMs}, a factor of
$\prognFiveNtGain\times$, which is \prognFiveNtAccuracy\% of the prediction.
A change that touches only how the results are written, and nothing about the
arithmetic or the reads, recovered almost exactly one quarter of the runtime.

\paragraph{Test 2: a reported number that is physically impossible.}
\texttt{toBW} hard-codes the $4N$ assumption. Applied to the non-temporal
variant it reports \prognFiveNtReported\,GiB/s --- above the
\prognFivePeakGiBs\,GiB/s that a single DDR4-2667 channel can physically
transfer. No kernel can exceed its own memory bus, so the only possible
conclusion is that this kernel is not moving $4N$ bytes. That is precisely the
claim. The formula is right for the shipped code and wrong for the
non-temporal version, which is the cleanest demonstration that the fourth $N$
is the read-for-ownership and not something intrinsic to \texttt{saxpy}.

\paragraph{Test 3: read the memory controller directly.} Both tests above
are indirect --- one infers the traffic from a time, the other from a number
that cannot be true. The integrated memory controller exposes counters
(\texttt{uncore\_imc/data\_reads} and \texttt{data\_writes}) that report actual
DRAM traffic, so the claim can be checked rather than deduced. Two corrections
are needed to use them: allocation, initialisation and verification each touch
memory once, so each kernel is run with 1 and with 21 repetitions and the
difference divided by 20; and the counters are system-wide --- the controller
cannot attribute a transfer to a process --- so the idle rate is sampled
separately and subtracted in proportion to elapsed time.

\ifdefined\prognFiveTablePerf
\prognFiveTablePerf

The ordinary-store kernel moves $\prognFivePerfStoreFpe$ floats per element
against a predicted $4$, and the non-temporal kernel
$\prognFivePerfStreamFpe$ against a predicted $3$ --- within 3\% and 7\% of the
model. The writes column is the sharper result: the ordinary-store kernel
writes $78.7$\,MiB per call, essentially exactly the
\prognFivePerfOneArray\,MiB of one array, which is what the $4N$ model requires
and what a first, faulty version of this measurement failed to show. The read
column falls by \prognFivePerfReadDrop\,MiB between the two strategies,
against a predicted drop of one array.

One row does not fit. The ISPC kernel reports $3.47$ floats per element where
$4$ is expected, despite issuing the same ordinary stores as the AVX2 kernel
that reports $\prognFivePerfStoreFpe$ and despite being slower than the
non-temporal version. This is not explained here, and it is left as measured
rather than adjusted or dropped. The comparison the extra-credit question turns
on --- \texttt{avx2\_store} against \texttt{avx2\_stream}, two kernels
differing in one instruction and measured identically --- is unaffected by it.
\fi

\subsection{Extra credit: improving \texttt{saxpy}}
\label{sec:prog5ec2}

The improvement follows from the analysis: since the kernel is bandwidth-bound
at \prognFiveBestFrac\% of peak, the only lever is total bytes, and the only removable bytes
are the read-for-ownership. Replacing the store with
\texttt{\_mm256\_stream\_ps} gives

\begin{quote}
\ms{\prognFiveStoreMs} $\rightarrow$ \ms{\prognFiveNtMs}, a
$\mathbf{\prognFiveNtGain\times}$ \textbf{speedup, on one core}, beating all
eight hardware threads of the shipped task version
(\ms{\prognFiveShippedTaskMs}) by $\prognFiveNtVsTasks\times$.
\end{quote}

Two implementation details matter. Chunk boundaries are forced to whole
64-byte lines, because a non-temporal store covering part of a line still
triggers the fetch it was meant to avoid, which would silently undo the
optimisation. And \texttt{\_mm\_sfence} is issued at the end of each thread's
range, since non-temporal stores are weakly ordered with respect to everything
else.

\paragraph{What the best possible implementation would achieve.} With $3N$
floats of traffic and the $\prognFiveBestDram$\,GB/s this machine has been
observed to sustain, the floor is
$240\,\text{MB} / \prognFiveBestDram\,\text{GB/s} = \ms{\prognFiveFloorMs}$. The measured
\ms{\prognFiveNtMs} is within $\prognFiveFloorGap\%$ of that floor, so there is essentially
nothing left to win on this hardware --- and the remaining gap is not worth
chasing, because it is smaller than the run-to-run spread of the shipped
program. Going faster requires a different memory configuration, not different
code. On a dual-channel machine of the same generation the same source would be
expected to run at roughly twice the speed, and only there would multi-threading
begin to pay.

\paragraph{What this program demonstrates.} Parallelism is not a universal
speedup. Programs 1--4 were limited by how work was divided, and every one of
them rewarded better division. \texttt{saxpy} is limited by a resource that
division cannot multiply, so the same techniques that were worth $6\times$
elsewhere are worth less than nothing here. Recognising which regime a kernel
is in --- by comparing its arithmetic intensity against the machine's ridge
point, which takes no measurement at all --- is what decides whether the next
hour is better spent on threads or on data movement. This program is also the
one place in the assignment where the machine's own configuration, a single
populated memory channel, sets the result more firmly than any code does.


%======================================================================
\section{Program 6: Making \texttt{K-Means} Faster}
\label{sec:prog6}
%======================================================================

The starter code clusters $M = 1{,}000{,}000$ points of dimension $N = 100$
into $K = 3$ clusters, and it is already correct --- the task is purely to find
where the time goes and remove it. The handout deliberately does not say where
to look. Two constraints shape everything that follows: only
\texttt{kmeansThread.cpp} may be modified, and \emph{only one} of
\texttt{dist}, \texttt{computeAssignments}, \texttt{computeCentroids} and
\texttt{computeCost} may be parallelised. Choosing which one is the whole
problem, and that choice has to be made on evidence rather than intuition.

\paragraph{Dataset.} All measurements use the supplied \texttt{data.dat},
804{,}002{,}420 bytes, whose MD5 checksum is

\begin{center}
\texttt{3a25f24193f4fdca82ee4cb2737fd5bb}
\end{center}

\noindent The file itself is not committed to the repository, on account of its
size.

\subsection{Step 1: measure before changing anything}
\label{sec:p6profile}

\texttt{CycleTimer} probes were placed around the three phases inside the main
loop, accumulating per-phase totals across the whole run and printing them when
\texttt{KMEANS\_PROFILE} is set. The run converges in \prognSixIters{}
iterations.

One measurement precaution proved necessary. The first profiled run reported a
total 11\% above the clean baseline, and the excess was spread across phases
that had not been touched. This is a 45\,W mobile part running a single-threaded
workload for roughly fifty seconds, which is long enough to heat it into a lower
turbo bin, so a run taken immediately after another is measurably slower. The
harness therefore profiles three times and keeps the fastest, consistent with
the minimum-of-$N$ rule used throughout this report. For the same reason the
later comparisons are run as interleaved rounds --- every configuration once
per round, minimum taken across rounds --- rather than all repetitions of one
configuration before moving to the next, so that drift is shared between
configurations instead of being charged to whichever one happens to run last.

\prognSixTableProfile

\begin{quote}
\textbf{\texttt{computeAssignments} accounts for \prognSixFPct\% of the
runtime.} It is the only phase large enough for Amdahl's Law to permit the
required speedup, so it is the one function to parallelise.
\end{quote}

The profile also explains \emph{why} the phases cost what they do, which
matters for knowing what can be recovered. \texttt{computeAssignments} performs
$K \times M = 3 \times 10^{6}$ calls to \texttt{dist}, \texttt{computeCost}
performs $M = 10^{6}$, and \texttt{computeCentroids} performs none --- it
streams $M \times N$ doubles and accumulates. The measured ratio of the first
two phases is close to the $3:1$ their call counts predict.

\paragraph{Why \texttt{dist} is slower than it looks.} Disassembling the
starter object file shows something worth knowing before trying to fix
anything. GCC does fold \texttt{pow(x,2)} into a multiply --- there is no call
to \texttt{pow} in the generated code --- and it does vectorise the subtract
and square into \texttt{vsubpd}/\texttt{vmulpd}. But the accumulation comes out
as a chain of scalar \texttt{vaddsd} instructions, because floating-point
addition is not associative and the compiler may not reorder the sum without
being told it can. Each \texttt{dist} call is therefore a dependency chain of
$N = 100$ additions at roughly four cycles of latency each: about 400 cycles,
and the arithmetic units sit idle between links. At $3\times 10^{6}$ calls per
iteration that predicts roughly $1.2\times10^{9}$ cycles, or \ms{310} at the
$3.881$\,GHz single-thread turbo recorded in Table~\ref{tab:p1clock}. The
measured cost is \ms{\prognSixAssignOrigIter} per iteration, about 10\%
above the estimate. A model this simple landing that close establishes the
dominant term: the phase is limited by the latency of a serial chain of
floating-point additions rather than by throughput.

It does not establish that the chain is the \emph{only} term, and it is not.
Section~\ref{sec:p6interchange} shows that roughly
\ms{\prognSixInterchangeSaved} of that \ms{\prognSixAssignOrigIter} is
memory traffic rather than dependency latency: it disappears when the loop
order changes, while the chain inside \texttt{dist} stays exactly as it was.
The estimate is best read as accounting for the bulk of the cost, not all of
it.

This matters because it tells us the phase is \emph{latency}-bound, not
bandwidth-bound. Latency-bound work is exactly the kind that parallelism
helps: eight threads run eight independent dependency chains at once.

\subsection{Step 2: what Amdahl's Law permits}

With $f = \prognSixF$ of the runtime in the one function we are allowed to
parallelise and $T = 8$ hardware contexts:

\[
S_{max} = \frac{1}{(1 - f) + \dfrac{f}{T}}
        = \frac{1}{\prognSixSerialFrac + \dfrac{\prognSixF}{8}}
        = \frac{1}{\prognSixSerialFrac + \prognSixFOverT}
        = \frac{1}{\prognSixDenom}
        = \mathbf{\prognSixSmax\times} .
\]

Two things follow immediately. The handout's $2.1\times$ target is achievable
but not comfortably --- it requires capturing
$2.1 / \prognSixSmax = \prognSixTargetFrac\%$ of the theoretical maximum, so a
merely adequate parallelisation will miss. And the $\prognSixSerialFrac$ of
runtime outside \texttt{computeAssignments} is untouchable under the
one-function rule, which fixes the ceiling no matter how well the rest is done.

\subsection{Step 3: the obvious parallelisation, and why it is the wrong one}

The starter code hands \texttt{computeAssignments} a range
\texttt{[args->start, args->end)} over the cluster index $k$, and its outer
loop runs over exactly that range. The structure is an invitation to split on
$k$, so that was tried first.

It requires more care than it appears to. Threads splitting on $k$ all write
the shared \texttt{minDist} and \texttt{clusterAssignments} arrays, so each
thread needs private copies and a serial merge afterwards to pick the winning
centroid per point. Implemented that way it is correct --- it converges in the
same \prognSixIters{} iterations --- and it does speed the phase up.

\begin{quote}
\textbf{Result: $\prognSixByKSpeedup\times$ overall} (\ms{\prognSixByKMs}),
short of the $2.1\times$ target.
\end{quote}

The reason is structural rather than a defect of the implementation:
$K = 3$. There are only three units of work on this axis, so at most three of
the eight hardware contexts can ever be busy, and five sit idle. The phase
itself sped up by $\prognSixByKAssignGain\times$ --- or
$\prognSixByKAssignGainAdj\times$ once one allows for the two phases this
variant does \emph{not} touch having also run \prognSixByKDrift\% faster in
that run, so part of the apparent gain is clock rather than threads. Either way
it is a reasonable return on three threads, but three threads is all the axis
allows. Additionally, splitting on $k$ keeps
the original loop order, in which each thread streams the entire 800\,MB data
array for its own $k$ --- so total memory traffic is unchanged while the merge
pass adds a new $M$-length scan.

The lesson is that the axis the code hands you is not necessarily the axis the
problem has. $K = 3$ and $M = 10^{6}$ are both available; only one of them is
larger than the machine.

\subsection{Step 4: parallelising over data points}
\label{sec:p6interchange}

The fix inverts the loops. Instead of \emph{for each centroid, scan every
point}, the code does \emph{for each point, compare against every centroid}:

\begin{verbatim}
for (int m = mStart; m < mEnd; m++) {
  const double *point = &args->data[(size_t)m * N];
  double best = 1e30; int bestK = -1;
  for (int k = args->start; k < args->end; k++) {
    double d = dist(point, &args->clusterCentroids[k * N], N);
    if (d < best) { best = d; bestK = k; }
  }
  args->clusterAssignments[m] = bestK;
}
\end{verbatim}

This one change does three things at once.

\begin{enumerate}
\item \textbf{It creates a million units of work instead of three.} Each thread
takes a contiguous range of $m$, so any thread count divides the work evenly
and every thread does identical work --- there is no load imbalance to manage,
unlike Program~1.

\item \textbf{It removes all sharing.} Each point's minimum is now a local
variable and each thread writes only its own slice of
\texttt{clusterAssignments}. The \texttt{minDist} array of $M$ doubles
disappears entirely, along with the merge pass that the $k$-split needed. No
locks, no atomics, no false sharing beyond one cache line at each range
boundary.

\item \textbf{It cuts memory traffic by a factor of $K$.} The original reads
the whole 800\,MB data array once per centroid; this reads each point once and
compares it against all three centroids while it is still in registers. The
three centroids are $3 \times 100$ doubles --- 2.4\,KB, permanently in L1.
Given what Program~5 established about this machine's memory system, this part
is not incidental: the original ordering moves $K \times \prognSixDataMB$\,MB per
iteration, which at the \prognFiveBestDram\,GB/s measured in Program~5 would
alone cost \ms{\prognSixOrigTrafficMs}.

This can be checked rather than asserted, and doing so closes the loose end
left in Section~\ref{sec:p6profile}. Running the interchanged code on a single
thread isolates the reordering from the threading:
\texttt{computeAssignments} falls from \ms{\prognSixAssignOrigIter} to
\ms{\prognSixAssignOneIter} per iteration, a saving of
\ms{\prognSixInterchangeSaved}. The same number of \texttt{dist} calls is
made either way and the dependency chain inside each is untouched, so the
saving can only be the $(K-1)$ extra passes over the data array that the
original made --- 1.6\,GB per iteration. That implies
$1.6\,\text{GB} / \prognSixInterchangeSaved\,\text{ms} =
\prognSixInterchangeGBs$\,GB/s, against the \prognFiveBestDram\,GB/s
Program~5 measured by an entirely different method on the same machine. Two
programs, two kernels, one memory system.
\end{enumerate}

\paragraph{Size of the change.} The handout estimates its own solution at
20--25 lines, and the change that matters here is about 35: the point-major
loop above, and the code that splits $[0, M)$ across threads. The file grows by
more than that because the \texttt{CycleTimer} instrumentation from step 1 is
kept, and because the original and the $k$-split implementations are retained
behind an environment variable so that every comparison in this section can be
reproduced from a single binary. Running \texttt{./kmeans} with nothing set
selects the final implementation.

\begin{quote}
\textbf{Result: $\mathbf{\prognSixSpeedup\times}$ overall}
(\ms{\prognSixBaselineMs} $\rightarrow$ \ms{\prognSixFinalMs}), against a
handout target of $2.1\times$ and an Amdahl ceiling of $\prognSixSmax\times$.
That is \prognSixFracOfSmax\% of the theoretical maximum.
\end{quote}

\prognSixTableVariants

Table~\ref{tab:prog6-profile} also carries a useful internal check. The two
phases that were \emph{not} modified, \texttt{computeCentroids} and
\texttt{computeCost}, cost within 1.7\% and 0.2\% of their original values
after the change. Nothing moved except what was meant to move, which both
validates comparing the two profiles against each other and rules out the
possibility that the speedup came from accidentally doing less work.

\texttt{computeAssignments} itself fell from \ms{34409.5} to \ms{5960.1}, a
factor of $\prognSixAssignGain\times$. That figure combines both changes ---
the loop interchange and the eight threads --- so it should not be read as a
parallel efficiency; Section~\ref{sec:prog6sweep} separates the two.

The sweep confirms the diagnosis, and the shape of the comparison is more
informative than a single number. Both curves flatten hard after four threads,
because by then the parallel part has shrunk to the point where the fixed
$\prognSixSerialFrac$ of serial work dominates everything else.

The measured curve \emph{crosses} the Amdahl bound at about five threads,
which is the visible result of two opposing effects. Below the crossing it runs
above the bound, which is not a contradiction: Amdahl's Law bounds what
parallelising a \emph{fixed} amount of work can achieve, and the loop
interchange reduced that work, so the measured curve is not bounded by a law
computed from the original workload. Above the crossing it falls slightly
below, because the threading does not achieve a perfect $1/T$ on the parallel
portion --- the same sub-linear scaling at high thread counts seen throughout
this report, and for the same reasons: SMT contexts are not full cores, and
turbo headroom is lost at full occupancy. The advantage from doing less work is
roughly constant, while the shortfall from imperfect scaling grows with $T$, so
one overtakes the other.

The $T = 1$ row separates the two contributions cleanly. With threading
switched off entirely, the final code still runs in
\ms{\prognSixOneThreadMs} against the original's \ms{\prognSixBaselineMs}
--- $\prognSixOneThreadSpeedup\times$ from the loop interchange alone, before
a single extra thread is involved. Threading the interchanged code then
contributes a further $\prognSixParallelOnly\times$, and
$\prognSixOneThreadSpeedup \times \prognSixParallelOnly = \prognSixSpeedup$.
Neither change would have reached the $2.1\times$ target by itself.

That middle factor is quoted against Table~\ref{tab:prog6-variants}'s
eight-thread time, so that the product returns the headline figure. Measured
entirely within the sweep --- its own $T=1$ against its own $T=8$ --- the same
quantity is $\prognSixSThread\times$, differing by the 3\% noted below. The
Karp--Flatt calculation in Section~\ref{sec:p6karp} uses that second form,
because it compares two endpoints of a single experiment.

One inconsistency is worth stating rather than hiding: the sweep's best
eight-thread run, \ms{\prognSixSweepBestMs}, is about 3\% faster than the
\ms{\prognSixFinalMs} recorded in Table~\ref{tab:prog6-variants} for the same
configuration. The two are separate experiments run at different times, and 3\%
is the run-to-run variation this workload shows on this machine. The headline
figure quoted above is the slower of the two, because it comes from the
experiment in which the original and the final implementation were measured in
the same interleaved rounds and are therefore directly comparable.

The profile after optimisation (Table~\ref{tab:prog6-profile}) shows the
bottleneck has moved. \texttt{computeAssignments} has fallen to
\prognSixAssignShareAfter\% and \texttt{computeCost} is now the largest phase
at \prognSixCostShareAfter\%. That is exactly where the remaining time is, and
it is exactly what the rules forbid touching: \texttt{computeCost} is a second
function, and the one parallelisation permitted has been spent. The only other
route --- reassociating the summation inside \texttt{dist} to break its
dependency chain --- is ruled out by the instruction not to change that
function's semantics. So $\prognSixSpeedup\times$ is close to the constrained
optimum, and the constraint, not the machine, is what now binds.

\subsection{Cross-check: the Karp--Flatt metric}
\label{sec:p6karp}

Amdahl's Law says what a given serial fraction permits. The Karp--Flatt metric
runs the inference backwards: given a measured speedup $S$ on $T$ threads, the
\emph{experimentally determined} serial fraction is

\[
e = \frac{\dfrac{1}{S} - \dfrac{1}{T}}{1 - \dfrac{1}{T}} .
\]

If $e$ matches the $f$ measured directly from the profile, the only thing
limiting the program is the serial fraction. If $e$ is larger, the excess is
parallel overhead that the profile did not see.

Applied to the headline result, $S = \prognSixSpeedup$ at $T = 8$ gives
$e = \prognSixKFNaive$, against a directly measured serial fraction of
$1 - f = \prognSixSerialFrac$. The two disagree by $\prognSixKFNaiveGap$.

That disagreement is worth taking apart, because it is \emph{smaller} than it
should be. Karp--Flatt assumes the serial and parallel versions do the same
work, and ours do not --- the loop interchange removed work, which inflates $S$
and therefore flatters $e$. Isolating the threading gives the honest figure.
Against the interchanged code running on one thread, whose own profile puts
$f = \prognSixFOne$ in \texttt{computeAssignments}, eight threads deliver
$S = \prognSixSThread$, so

\[
e = \prognSixKFFixed \quad\text{against}\quad 1 - f = \prognSixSerialFracOne ,
\]

a gap of $\prognSixKFFixedGap$ rather than $\prognSixKFNaiveGap$. So there is
real parallel overhead --- roughly six points of apparent serial fraction ---
and the naive application of the metric \emph{understated} it by about half.
The overhead is of the expected kind: thread creation and join on every one of
the \prognSixIters{} iterations, four of the eight contexts being SMT siblings
rather than physical cores, and the loss of turbo headroom at full occupancy
measured in Table~\ref{tab:p1clock}.

The two metrics answer different questions. Amdahl's Law bounded what was worth
attempting before any code was written. Karp--Flatt says how much of the
shortfall against that bound is overhead rather than structure --- but only if
the comparison holds the work fixed, which is exactly the assumption an
optimisation like the loop interchange breaks.

\subsection{Correctness}

Three independent checks, since a faster wrong answer is worthless:

\begin{itemize}
\item \textbf{Iteration count.} All three implementations converge in exactly
\prognSixIters{} iterations. Convergence is decided by \texttt{stoppingConditionMet}
comparing per-cluster costs against $\epsilon$, so an identical count across a
hundred iterations means the cost vector followed an identical trajectory.
\item \textbf{No reordered arithmetic.} \texttt{dist} is called unmodified and
each point's comparisons happen in the same order as before, so the
floating-point results are bit-identical rather than merely close. The
parallelisation partitions $m$, and no partial sums cross threads.
\item \textbf{Visual check.} \texttt{plot.py} output
(Figure~\ref{fig:prog6kmeans}) shows three well-separated clusters with
centroids at their centres, matching the reference images in the handout.
\end{itemize}

\paragraph{What this program demonstrates.} The speedup came from one
structural change, not from tuning: the original code was parallel along an
axis of length three on a machine with eight contexts, and the fix was to
notice that the same computation is also parallel along an axis of length a
million. Profiling first is what made that visible --- without the per-phase
breakdown there would have been no reason to prefer
\texttt{computeAssignments}, and no way to know that Amdahl's Law left only
$\prognSixSmax\times$ on the table before any code was written. It is also the
clearest illustration in this assignment that the bound moves: having removed
the original bottleneck, the program is now limited by a phase the rules do not
allow us to touch.
